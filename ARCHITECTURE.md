# ARCHITECTURE — текущее состояние, триггеры, варианты бэкенда

Документ-решение, **не план реализации**. Цель — зафиксировать, в какой точке мы
сейчас находимся, при каких условиях имеет смысл уезжать на бэкенд, и какие
варианты тогда стоит сравнить. Менять архитектуру стоит только когда хотя бы
один триггер ниже стал реальной проблемой, а не теоретической.

---

## 1. Текущая модель (как сейчас)

```
Браузер
 ├─ HTML/CSS/JS (статика, без сборки)
 ├─ IndexedDB           ← основное хранилище: users, progress, settings
 └─ localStorage        ← pointer на активного пользователя + старые ключи тренажёра
```

**Запуск:** `python3 -m http.server` в `app/`, или просто открыть `index.html`.

**Что работает хорошо:**

- Ноль зависимостей, ноль деплоя, ноль ежемесячных счетов.
- Полный оффлайн-режим из коробки.
- Скорость: всё локальное, мгновенный отклик на любую проверку упражнения.
- Приватность: данные не покидают устройство.
- Резервное копирование: ручной экспорт/импорт JSON через шапку профиля.

**Где модель упирается в стену:**

| Ограничение | Симптом |
| --- | --- |
| Нет синхронизации между устройствами | Прошёл модуль на ноуте — на телефоне его «нет», пока не выгрузил/загрузил JSON. |
| Нет настоящей аутентификации | PIN — защита «от младшей сестры», не более. Если отдать .json чужому — данные открыты. |
| Нет аналитики над прогрессом | «Слабые темы по неделям», «когда я в среднем учился» — приходится считать руками. |
| Нет серверных интеграций | Нельзя позвать LLM из браузера без утечки ключа; нельзя отправить себе напоминание. |
| Контент только в `data/textbook/u<NN>.js` | Добавление модуля = пуш в репозиторий. Не блокер на 5 модулях, неудобно на 50+. |

## 2. Триггеры миграции

Идти в бэкенд имеет смысл, когда хотя бы **один** из этих сценариев из «было бы
неплохо» становится «уже мешает»:

1. **Синк между ≥2 устройствами без ручного JSON.** Самый частый и самый
   законный повод. Решается дешевле всего.
2. **LLM-проверка свободного ответа** («объясните правило своими словами» →
   модель ставит оценку и подсказку). Из браузера это делать нельзя без
   утечки ключа.
3. **Многопользовательский режим с реальной аутентификацией** (учитель —
   ученики, или несколько учеников у репетитора).
4. **Push/email-напоминания** «пора повторить тему» по интервальной
   логике — нужен крон где-то снаружи браузера.
5. **Аналитика и отчёты** через SQL/BI поверх прогресса.
6. **Веб-админка для контента** (правка модулей через интерфейс, без
   правки `data/textbook/u<NN>.js` руками).

Если ни один из этих пунктов не «жмёт» — менять ничего не нужно. Текущая
схема живёт в проде у многих образовательных проектов годами.

## 3. Целевые конфигурации

### Phase 1 — managed (рекомендуется при первом триггере)

```
Браузер (PWA)
 │  service worker — оффлайн-кеш
 │  IndexedDB — локальный буфер прогресса
 │  fetch() ──► provider API (REST/GraphQL)
 │
 ▼
Cloudflare D1 (SQLite) + Workers   *или*    Supabase (Postgres + Auth + Realtime)
 ├─ users / progress / settings
 ├─ Auth: magic-link или OAuth (Google)
 └─ Edge-функции для LLM-вызовов с серверным ключом
```

**Почему managed.** Сейчас цель — учиться испанскому, а не администрировать
Linux. У managed-провайдеров поддержка БД, миграций, бэкапов, TLS, домена,
auth — встроенная и не требует ничего, кроме `wrangler deploy` или
`supabase deploy`.

**Стек:**

- **Фронт:** тот же ванильный HTML/CSS/JS + service worker для оффлайна
  (Workbox или 30 строк руками). PWA-манифест → можно «установить» на
  телефон как нативное приложение.
- **БД + API:** один из двух —
    - **Cloudflare D1 + Workers + R2.** SQLite-as-a-service (бесплатный
      тариф: 5 ГБ, 25M чтений/мес), Workers для эндпоинтов, R2 для
      файлов аудио/картинок если появятся. Минимум магии, чистый
      SQL под капотом.
    - **Supabase.** Postgres + auth + realtime + edge functions в одной
      коробке. Бесплатный тариф щедрый. Удобнее, если захочется
      realtime-фич («учитель видит, что я отвечаю прямо сейчас»).
- **Auth:** magic-link на email — минимальное трение, никакого пароля.
  Опционально — Google OAuth.
- **LLM:** Anthropic API (или другой) вызывается с edge function, ключ
  хранится в env-переменных провайдера.

**Стоимость:** \$0/мес на бесплатных лимитах для одной семьи; \$5–10/мес
если упрёмся (вряд ли скоро).

**Время до P1:** ~2 рабочих дня.

- День 1: схема D1/Postgres, один Worker/Edge function для CRUD прогресса,
  переписывание `js/db.js` на «IndexedDB как кеш + fetch на сервер»,
  service worker.
- День 2: auth (magic-link), миграция данных из существующего JSON-экспорта
  (схема та же — это уже было заложено сознательно), деплой, проверка
  с двух устройств.

**Что не меняется:** структура `data/textbook/u<NN>.js`, рендер теории
и упражнений, сам учебник. Всё это остаётся клиентским.

### Phase 2 — full self-host (если managed станет тесно)

```
VPS (Ubuntu, 1 vCPU / 2 GB / 40 GB SSD ≈ \$5–7/мес)
 ├─ Caddy — TLS + reverse proxy
 ├─ Docker Compose:
 │    ├─ FastAPI (Python) или Hono (TS) — REST API
 │    ├─ Postgres 16 — БД (или SQLite + Litestream для бэкапов)
 │    ├─ Redis (опц.) — кеш / очередь напоминаний
 │    └─ статика учебника на том же домене
 └─ Прометей + Loki (опц.) — мониторинг
```

**Когда имеет смысл:**

- Не устраивают TOS managed-провайдера или хочется максимум приватности.
- Нужен фоновый воркер с долгими задачами (например, ночная переиндексация
  упражнений на «слабые темы» через LLM).
- Хочется учебная цель — пощупать админку.

**Стек минимально-достаточный:**

- **Веб-сервер:** Caddy — автоматический Let's Encrypt, конфиг в одну
  страницу.
- **Бэкенд:** FastAPI + SQLAlchemy + Alembic (если Python),
  или Hono + Drizzle (если хочется TS на бэке тоже).
- **БД:** Postgres 16 в контейнере. Бэкап — `pg_dump` ночной cron в R2
  или Backblaze.
  Альтернатива: **SQLite + Litestream** — стримит WAL в S3-совместимое
  хранилище, простой single-file disaster recovery.
- **Auth:** один из:
    - своё magic-link (60 строк),
    - Authelia как сторонний контейнер,
    - Cloudflare Access перед всем поддоменом (zero-config SSO, бесплатно).
- **Деплой:** `git push` → GitHub Action → SSH в VPS → `docker compose pull && up`.
  Или просто вручную, для одной семьи и сошёл бы.

**Стоимость:** \$5–10/мес на VPS + домен (\$10/год).

**Время до P2:** ~5 рабочих дней + регулярная (раз в 1–3 мес) обвязка
обновлений ОС/контейнеров. Это и есть основной аргумент *против* P2:
self-host = постоянный налог временем.

## 4. Миграция данных

Принципиально **уже готова на 80%**: JSON-экспорт IndexedDB, реализованный
в `app/js/db.js`, имеет ровно ту же форму, что нужна для импорта на сервер.

Шаги:

1. Пользователь нажимает «Экспорт всех профилей» в шапке.
2. Загружает .json в форму на сервере (или CLI скрипт).
3. Сервер парсит и пишет в свою БД, схема:

   ```sql
   create table users (
     id          uuid primary key,
     name        text not null,
     avatar      text,
     created_at  timestamptz default now(),
     -- pin_hash убран: на сервере берём настоящий auth (magic-link)
     auth_email  text unique
   );
   create table progress (
     id              bigserial primary key,
     user_id         uuid references users(id) on delete cascade,
     unit_id         text not null,
     exercise_id     text not null,
     question_id     text not null,
     attempts        int not null default 0,
     last_answer     text,
     last_is_correct bool,
     ever_correct    bool not null default false,
     first_solved_at timestamptz,
     last_attempt_at timestamptz,
     unique (user_id, unit_id, exercise_id, question_id)
   );
   create table settings (
     user_id uuid references users(id) on delete cascade,
     key     text not null,
     value   jsonb,
     primary key (user_id, key)
   );
   ```

4. После миграции: фронт переключается на серверный API, IndexedDB
   становится оффлайн-кешем («write-through» при синке, «read-from» при
   отсутствии сети).

**PIN никуда не уезжает.** На сервере берётся настоящий auth (magic-link
или OAuth) — PIN был костылём для статической версии.

## 5. Сравнение по 6 критериям

| Критерий | Сейчас | P1 managed | P2 self-host VPS |
| --- | --- | --- | --- |
| Время до запуска | 0 (готово) | ~2 дня | ~5 дней |
| Постоянное обслуживание | 0 | минимальное (раз в полгода обновить SDK) | регулярное (обновления, мониторинг) |
| Деньги | \$0 | \$0–10/мес | \$60–120/год VPS + домен |
| Синк устройств | ручной (JSON) | автоматический | автоматический |
| Реальная аутентификация | PIN | да (magic-link) | да (любой, включая SSO) |
| LLM-фичи | нет | да | да |
| Полный контроль | да (локально) | средний (TOS провайдера) | да |
| Приватность данных | максимальная (только локально) | средняя (у провайдера) | максимальная (свой VPS) |

## 6. Рекомендация

1. **Сейчас:** ничего не менять. Текущая модель окупает свою сложность
   для личного учебного проекта 1–3 пользователей.
2. **Когда сработает первый триггер** (вероятнее всего — синк между
   ноутбуком и телефоном): идти в **P1 managed** на Cloudflare D1 + Workers.
   ~2 дня работы и нулевая стоимость поддержки.
3. **К P2 — VPS** идти, только если managed реально упрётся в потолок
   или появится мотивация «хочу полный self-host». Раньше — это
   преждевременная оптимизация, которая будет отнимать время от учёбы
   испанского.

## 7. Открытые вопросы (на потом)

- **Контент модулей:** хранить в репозитории как сейчас (`data/textbook/u<NN>.js`)
  или вынести в БД? Пока — в репо, версии через git, ревью через PR.
  Перенос в БД оправдан только если появится веб-админка для правки контента
  не-разработчиками.
- **Аудио:** SpeechSynthesis сейчас даёт «системный голос», качество
  плавает. На бэкенде можно генерировать MP3 через ElevenLabs / OpenAI TTS
  и кешировать в R2 — это даёт стабильное звучание, но добавляет затрат.
- **Геймификация:** очки, серии, цели — функция чисто фронтовая, можно
  делать и до миграции на бэк.
